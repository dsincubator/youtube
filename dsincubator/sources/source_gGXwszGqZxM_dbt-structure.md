# dbt structure

## Summary

This final video in a three-part dbt basics series explains the minimal structure required for a dbt project, linking structure to the basic usage commands covered earlier (`run`, `test`, `docs generate/serve`). The presenter walks through three essentials — two YAML files and one directory — and then demonstrates how that minimal scaffold expands once dbt commands are run.

The first file is `profiles.yml` (caption "profiles yaml" ← `profiles.yml`) which defines connections between the dbt project and a database. It typically lives under the hidden `~/.dbt/` directory in the user home (caption "this file typically lives under your user home directory under the hidden file hidden directory. DVD" ← `~/.dbt/`) because it holds secrets such as passwords. The demo profile is named `hello_world` (caption "hello world is just the name that I gave to the profile" ← `hello_world`) with a target `dev` that connects to a DuckDB database (caption "Duc TB database ... DuckDB" ← `DuckDB`). DuckDB is chosen because it is powerful, requires minimal configuration, runs locally, and needs no password or paid hosted service, ideal for experimenting without commitment. Fields inside the profile define the connection.

The second file is `dbt_project.yml` (caption "DBT project Yama is the main configuration file" ← `dbt_project.yml`) — the main configuration that tells dbt where transformation files live and where the transformed dataset should go. Its `profile` field must match the profile name defined in `profiles.yml` (caption "profile field maps to ... name of the profile defined in the profiles yamal file ... if you change that ... to something that doesn't really match so let's say bad then ... The header also contains `name` and `version` (project evolution) versus the dbt version field (caption "first version ... you can change to show evolution of your project but this one ... refers to the version of DVT that you are running" ← `version`). The middle section declares directories: `model-paths` set to `models` and `target-path` (caption "first we have the SQL files that Define the Transformations ... second the target directory where the transform database will go" ← `models` / `target`).

The third element is the `models` directory (caption "models is the directory where you typically put the SQL files that Define ... Transformations" ← `models/`), typically containing one or more `.sql` files. The example `model.sql` is minimal: `select 'hello world' as greeting` (caption "creates a string called hello world and assigns it to a variable called greeting" ← `select 'hello world' as greeting`), noting real projects would select/transform columns from source tables. The terminal demo with `tree` confirms the minimal scaffold (ignoring two `.md` teaching files, and cleaning `logs/` left by a trial `dbt test` with `logs` directory — caption "this logs directory there I think it was generated by when I tried to do ... Running `dbt run` materializes the SQL transformations: row data from the database is transformed and written into the `target` directory (caption "once you do a DVT run ... ## Key Concepts & Tools Taught

- **[dbt]:** Open-source transform tool whose minimal project is two YAML configs plus a `models` folder of SQL; basic commands are `dbt run` to materialize transforms into `target/`, `dbt test` for integrity, and `dbt docs generate` / `dbt docs serve` for documentation and serving (caption "when we run a DBT command ... there will be new directories ... as a consequence" ← `dbt run` / `test` / `docs`).
- **[profiles-yml]:** Connection file `profiles.yml` (caption "profiles yaml defines the connections between your DBT project database" ← `profiles.yml`) living under `~/.dbt/` (caption "hidden directory. DVD ... typically leaves because typically it connects to databases through Secrets" ← `~/.dbt/`), containing the profile `hello_world` → target `dev` → DuckDB connection block.
- **[dbt-project-yml]:** Main config `dbt_project.yml` (caption "DBT project Yama is the main configuration file where you tell DBT where ... files that transform your data leave and where the transformed data set should go" ← `dbt_project.yml`) where `profile: hello_world` must match `profiles.yml`'s profile name or `dbt test` errors, plus `name`, `version`, `model-paths: [models]` and `target-path: target`.
- **[duckdb]:** Local analytical database requiring no password (caption "I'm using a Duc TB database which is really nice that not only is ... powerful but also because it requires very minimum configuration and it can run locally so I don't need any password" ← `DuckDB` / `duc tb`) used as the `dev` target for cost-free experimentation.
- **[models]:** Directory of SQL transform files (caption "models is the directory where you typically put the SQL files that Define the SQL Transformations ... that you want to your table to undergo" ← `models/`), example `models/model.sql` containing `select 'hello world' as greeting` (caption "creates a string called hello world and assigns it to a variable called greeting" ← `select 'hello world'`).
